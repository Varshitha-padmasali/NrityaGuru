# Corrective feedback (Part 8)

    POST /api/feedback/generate   {"session_id": "..."}

Code: `api/feedback.py`, `services/feedback_service.py` (orchestration), `feedback_evidence.py` (evidence items),
`feedback_prompt.py`, `feedback_validation.py` (guards), `feedback_fallback.py` (evidence-only answer), `schemas/feedback.py`.

## Trust model
The request carries ONLY a session id. Evaluation data is loaded from the trusted store (Part 7). Extra fields in the body
(for example fake `predicted_labels`) are ignored; there is a test for that. Gemini receives structured results only and
never analyses a video; the response carries a disclaimer saying so.

## Flow
session id -> EvidenceService (store, version, reference lookup, assessment) -> evidence items (numbered facts)
-> level `insufficient`? skip Gemini -> prompt -> Gemini -> parse -> shape check -> guards -> result.
Any failure returns **evidence-only** feedback built from fixed templates.

## Evidence items
Plain-language facts built by code from supplied fields only, with stable ids: `reference`, `reference_instructions`
(only if instructions exist), `label`, `dtw`, `deviation:<id>`, `landmarks`, `warning:<n>`, `mock_notice`.
Gemini must cite these ids in every observation and suggestion.

## Guards on Gemini's output (heuristics, not proof of faithfulness)
1. Every observation/suggestion cites at least one existing evidence id.
2. No body-part word (thumb, finger, wrist, ...) or video/camera word unless the evidence itself uses it.
3. No number unless it appears in the evidence (a 0-1 value may be written as a percentage).
Not covered: wrong mudra names, or wording that distorts a real finding. Human review is still required.
Strict by design: if Gemini adds "hold for 3 seconds", the AI text is discarded and the learner gets the evidence-only answer.

## Limitations are never left to the model
`feedback.limitations` always equals the deterministic assessment limitations (low confidence, unreliable landmarks,
mismatch without detail, DTW meaning, missing instructions, unverified reference, evaluation warnings, MOCK data).
Gemini is only asked for the summary, observations and suggestions.

## Response
`mode` ai | evidence_only, `session_id`, `reference`, `evidence_level`, `is_mock`, `feedback` (overall_summary, observations[],
suggestions[], limitations[]), `supporting_evidence[]`, `model`, `fallback_reason`, `notice`, `disclaimer`.

## Status codes
| Code | When |
|---|---|
| 200 | OK, also when Gemini failed (mode evidence_only) or the evidence was insufficient |
| 404 | `session_not_found` |
| 422 | bad session id, `malformed_result`, `unsupported_version`, `unknown_reference` |
| 429 | rate limit (shared with the tutor endpoint) |
| 502 / 500 | `session_mismatch` / `mock_data_in_real_store` |
| 503 | `store_unavailable` (evaluation integration not configured) or database down |
Error bodies: `{"detail": "...", "code": "<evaluation error code>"}`.

## Design note
When the evidence level is `insufficient`, the observations only state the reason (for example unreliable
landmarks). A finding such as a label "match" built on unreliable data is not presented as a result; it remains visible
in `supporting_evidence` for transparency.

## Known gaps
- No authentication yet: anyone who knows a session id can read its feedback. The evaluation module must use unguessable ids
  (UUID4) until login exists.
- Feedback is not stored yet (Part 9).
- Guard word lists are English only and can reject harmless text (the safe direction).
- `evaluation module` is MOCK data until your teammate delivers real results.
